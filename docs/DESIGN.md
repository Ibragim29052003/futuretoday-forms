# Решение и границы MVP

## Выбор главного

Основной результат — менеджер может самостоятельно пройти путь от идеи формы до первых ответов. Поэтому реализованы создание, публикация, заполнение и просмотр откликов. Добавлена небольшая воронка, поскольку в исходной проблеме прямо упомянуты незавершённые формы. Продуктовые гипотезы: один вопрос на экран и понятный прогресс могут снизить ощущение объёма; эффект не заявляется как доказанный и требует сравнения с контрольным вариантом.

Не добавлены загрузки файлов, ветвление вопросов, email-уведомления, аккаунты и сложные отчёты. Они увеличили бы время проверки и число зависимостей без необходимости для ключевого сценария. Пример формы позволяет быстро увидеть результат после запуска; вымышленных откликов и искусственной статистики в поставке нет.

## Архитектура

Один процесс Node.js обслуживает интерфейс и REST API с одного origin. Модули HTTP, crypto, fs и тестовый раннер встроены в Node.js. Это обеспечивает требуемые две команды запуска без сборки, внешней СУБД, регистрации или облачного сервиса.

JSON подходит для малого автономного MVP. Каждая мутация работает с копией состояния, ожидает очередь, сохраняет файл и только после успешной записи публикует снимок в памяти. Ответ клиенту отправляется после записи. Чтение не видит полузаписанного состояния. При росте объёма полная перезапись JSON и копирование состояния станут ограничением; следующий шаг — транзакционная SQLite с миграциями. Текущая схема сознательно рассчитана на один процесс, а не на кластер.

## Версии и повторные действия

У формы есть редактируемый `draft`, опубликованный снимок и ревизия для optimistic concurrency control. Каждое сохранение проверяет ревизию; устаревшая вкладка получает 409. Ссылка остаётся прежней. Новая публикация изменённых вопросов создаёт новую версию; идентичная публикация — нет.

Посещение хранит снимок версии на момент открытия. Это позволяет отправить ответы из уже открытой вкладки после обновления формы без потери контекста. Каждый отклик также хранит этот снимок: переименование или удаление вопроса в черновике не меняет историю. Закрытие формы прекращает все новые отправки, включая старые вкладки. Повторное открытие сохраняет ссылку и версию.

Один `sessionId` может создать один отклик. Повтор после потерянного сетевого ответа безопасен: сервер возвращает существующий ID. Это не дедупликация людей: студент может открыть новую вкладку и подать ещё один отклик. Для реального конкурса правило уникальности нужно отдельно согласовать с бизнесом.

## Проверка и данные

Сервер проверяет схему, обязательность, длины, email, варианты списка, тип отметки, неизвестные вопросы и принадлежность посещения форме. Доверия только к проверке в браузере нет. Значения экранируются при вставке в HTML; CSP запрещает внешние/встроенные скрипты. Из CSV нейтрализуются формулы. Публичные API не возвращают ответы; административные маршруты открыты согласно заданию.

Сервер привязан к loopback, проверяет Host/Origin, блокирует cross-site мутации и ограничивает публичные запросы. Это защита локального демо, а не замена авторизации. При реальном развёртывании нужны аутентификация, роли, HTTPS, правила работы с персональными данными, журнал доступа, резервирование и ограничение срока хранения. Автоматическое удаление данных в MVP не выполняется.

## Следующая итерация по результатам проверки гипотез

1. На основе воронки найти вопросы с частыми остановками, проверить их формулировки, необходимость и мобильное удобство.
2. Измерить конверсию до/после сокращения формы при сопоставимом источнике трафика. Сегментация и качественные интервью помогут понять причины.
3. При реальных объёмах перенести данные в SQLite и добавить резервное копирование.
4. При выходе за локальную проверку добавить защищённую админку и согласованный процесс обработки данных.
